The problem

Sentry is powerful, but its API is hostile to an agent's context window.

Raw events are enormous

A single Sentry event endpoint can return 100K+ tokens — more than most models can hold.

Manual & time-consuming

Copy-paste, clicking around, exporting data — slow and error-prone.

Direct to your Sentry

The server talks only to your Sentry instance. Tool results go to whichever LLM client you connect, and on to its model provider.

Buried debugging signal

Stack frames, breadcrumbs and missing dSYMs sit deep inside payloads full of noise.

What it does

An MCP server that exposes your Sentry data to AI assistants, sized for their context window.

Issues & Events

List, search and inspect issues and events with Sentry query syntax.

Stack frames

Structured frames pulled out of the event, with an in-app-only filter.

Breadcrumbs

The trail of events leading up to an error, filterable by type.

dSYM checks

Spot missing iOS/macOS debug symbols and Android ProGuard mappings.

Grouping & releases

Fingerprint hashes, per-event grouping breakdowns, release health and distributed traces.

Token-aware

Field filters, grep patterns, stack truncation and cursor pagination. List and detail tools apply a 50k-token budget.

Quickstart (1 minute)

Configure your AI client to use the MCP server.

1

Create a Sentry auth token

Settings → Auth Tokens. Grant org:read, project:read, team:read, event:read and project:releases.

2

Add it to your client config

Pick your client below. Each tab shows where the file lives.

3

Start querying

Ask “list unresolved issues in my-project” to confirm the server loaded.

Use 1.2.0 or later. Earlier versions are deprecated: they can send your Sentry token to arbitrary hosts through raw_sentry_api and ignore SENTRY_READ_ONLY. If you ran one with an agent, rotate the token. See the changelog.

npm still serves 1.1.2 for now. Until the npm release lands, replace selfhosted-sentry-mcp@latest in the config with the v1.2.0 GitHub release tarball: https://github.com/HieuAnh87/sentry-selfhosted-mcp/releases/download/v1.2.0/selfhosted-sentry-mcp-1.2.0.tgz

Project scope → .mcp.json in your repo root — gitignore it, it holds a token. User scope → claude mcp add --scope user, which keeps it out of the repo entirely.

{
  "mcpServers": {
    "sentry": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "selfhosted-sentry-mcp@latest"],
      "env": {
        "SENTRY_URL": "https://sentry.yourcompany.com",
        "SENTRY_AUTH_TOKEN": "<your-token>",
        "SENTRY_ORG_SLUG": "your-org",
        "SENTRY_READ_ONLY": "true"
      }
    }
  }
}

Raw API (1)

  • raw_sentry_apiWRITE

WRITE marks tools that can modify Sentry. raw_sentry_api accepts GET, POST, PUT and DELETE, so it can reach any endpoint your token permits. SENTRY_READ_ONLY=true hides and refuses the four mutating tools and restricts raw_sentry_api to GET — it is opt-in, and off by default.

Trust & Safety

Know where your data goes.

Self-hosted

Runs on your machine and talks only to your Sentry instance. Results are sent to whatever LLM client you connect.

Token-based auth

Uses your Sentry auth token, read from the environment. No password, no storage.

Read-only mode

Five tools can write to Sentry. SENTRY_READ_ONLY=true blocks them; it is opt-in, not the default. Bulk updates refuse to run without a query or an explicit ID list.

Open source

MIT licensed and auditable. See SECURITY.md for token scoping guidance.
